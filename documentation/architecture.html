System Architecture

A high-level tour of how DecentEdu is put together — the technology stack, how the front end talks to the back end, how branches are kept isolated, and how heavy jobs like result processing and PDF reports run without slowing the app down. Written to be useful to both non-technical stakeholders and developers.

The big picture

DecentEdu is a modular monolith: one application and one database, cleanly split into feature modules (Academic, Students, Fees, Examinations, …). It exposes a versioned REST API that a React single-page application (SPA) consumes. There is no page reload as you move around — the SPA fetches JSON and renders instantly.

React SPA (browser)→ REST API /api/v1→ Module logic→ MySQL (one DB)

Slow or bulk work (report PDFs, bulk imports, SMS sending, attendance ingestion) is pushed onto a queue and processed by background workers, so the interface stays responsive.

🧩

Why one app, not microservices? The domain is densely relational — a single marksheet touches student, enrolment, class-config, subject, grade scale, exam config and branch; a fee receipt posts to the general ledger. These are transactional, same-request joins. One database with ACID transactions is simpler, cheaper and more correct than a distributed system at this scale.

A request, end to end

Every authenticated API call passes through the same pipeline. Using bulk mark entry as an example:

  1. The SPA sends the request
    With the session cookie and an XSRF token — e.g. POST /api/v1/examinations/marks.
  2. Authentication
    auth:sanctum confirms a valid session.
  3. Branch context
    The branch middleware resolves your active branch, checks you're a member, and sets it as the tenancy + permission “team”.
  4. Permission check
    The route requires a permission (here examinations.manage); it's rejected if you lack it.
  5. Validation
    A Form Request validates the payload (mark ≤ total, absent XOR mark, roll ownership).
  6. Business logic
    An Action/Service performs the write inside a database transaction and may fire domain events.
  7. Response envelope
    A consistent JSON shape is returned (see below) and the SPA updates its cache.

Consistent API envelope

Every endpoint answers with the same structure, so the front end handles success and failure uniformly.

// Success
{ "success": true,  "message": "Fee collected.", "data": { … }, "meta": { … } }

// Failure
{ "success": false, "message": "Validation failed",
  "error_code": "VALIDATION", "errors": { "amount": ["Amount exceeds the due balance."] } }

Multi-branch isolation

DecentEdu supports many schools under one deployment using row-level tenancy: every business record carries a branch_id, and the system automatically filters every query to the active branch.

The hierarchy is two levels:

Organization→ Branch (campus)→ Everything else

Isolation is enforced in three layers (defence in depth):

  1. Middleware resolves and verifies the active branch on every request.
  2. A global query scope adds WHERE branch_id = <active> to every read and stamps it on every write — a developer cannot forget it.
  3. Policies & route binding re-check a loaded record's branch before any action, guarding against ID guessing (IDOR).

Cross-branch reporting is possible only through explicit, permission-gated aggregation that opts out of the scope deliberately — never by accident.

✅

Practical effect. While “Demo College” is active, requesting a “Demo School” student by ID returns not found — the row is simply invisible. There is no way to leak data across branches through the normal API.

How modules are organized

Code is feature-first, not layer-first. Controllers live under app/Http/Controllers/Api/<Module>/ and models under app/Models/<Module>/, and the React side mirrors this exactly under resources/js/features/<module>/. A developer works one vertical slice end-to-end.

Two patterns keep things DRY:

  • Generic Setup controllers. Dozens of near-identical “reference table” resources (classes, shifts, sections, designations, fee heads, exams…) are served by one SetupController per module behind a whitelisted {resource} slug, instead of one controller each.
  • A report registry. All PDF/Excel reports are reached through one endpoint whose slug is validated against a registry — adding a report means registering a class, not adding a route.

Events & cross-module side-effects

Modules stay decoupled by communicating through domain events rather than reaching into each other. The clearest example: collecting a fee raises a FeeCollected event, and an Accounting listener posts the matching receive voucher to the general ledger. Fees never needs to know how Accounting works.

Fee collected→ FeeCollected event→ Accounting listener→ Receive voucher in GL

Performance & reliability

Queues
Result processing, report generation, bulk import, SMS send and attendance ingestion run as background jobs so requests stay fast.
Caching
Hot, rarely-changing data — permission maps, branch settings, reference lists, dashboard counters — is cached with short TTLs.
Idempotency & transactions
Multi-row writes (bulk registration, mark save, result process, fee collection) are wrapped in a single DB transaction; sensitive endpoints are safe to retry.
Audit trail
Sensitive operations (mark edits, fee collection, user/permission changes) are recorded to an audit log for dispute resolution.
Throttling
Bulk import, SMS send and report endpoints are rate-limited to protect the system and paid resources.
