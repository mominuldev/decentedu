Data Model

How DecentEdu's information is structured. This page explains the two ideas that hold the whole schema together — the class-config and the per-year enrolment — then walks the entity groups and their relationships.

Conventions

Every business table follows the same rules:

  • branch_id on every tenant-owned row — the isolation backbone.
  • Bilingual + ordering on reference tables: name, name_bn, serial, status.
  • Soft deletes on masters and financial/academic records — deletions are reversible.
  • Audit stamps: created_by, updated_by, timestamps.
  • Money as DECIMAL(12,2), marks as DECIMAL(6,2).

The join backbone

Two structures make everything else correct:

Class Config — the shared teaching unit

A class config is a concrete section of teaching: the combination of (branch, class, shift, section). It is the hub that attendance, class routines, exam configuration, fee structures and subject-teacher assignments all point at — so a “section” is one row everyone shares.

Class (e.g. Nine)× Shift (Day)× Section (A)= Class Config

Enrolment — placement per academic year

A student's identity is permanent, but their class, section and roll change every year. So DecentEdu separates identity (the students table) from placement (a student_enrollments row per academic year). This is what makes year-end promotion, historical results and multi-year reporting correct — nothing is destructively overwritten.

students (identity)  1───∞  student_enrollments  ∞───1  class_configs  ∞───1  academic_years
                                     │                        ├──1 classes
                            roll, group_id,                   ├──1 shifts
                            category_id, is_current           └──1 sections
🔑

Uniqueness rules enforced here: one placement per student per year, and a roll is unique within a class-config for a given year.

Key relationships

Org → Branch → everything
Two-level tenancy; all business rows carry branch_id.
Student vs Enrolment
Identity is permanent; placement is per session — clean promotion history and correct historical fees/results.
Class Config as hub
Attendance, routines, exam config, fee config and subject-teacher all reference the same class-config row.
Fees → Accounting
A fee collection raises a voucher (via an event) so the general ledger is the single source of financial truth.
Exam chain
exam_config → mark_config → marks → results → summary (GPA + position), with per-class grades and the 4th-subject feeding GPA.
CMS content
Pages/Posts/Notices/Events carry SEO + drag-ordered content blocks; taxonomies & terms categorize them; menus link them.

FEE_HEAD ─< FEE_SUB_HEAD ─< FEE_CONFIG ─> STUDENT_FEE

🧱

Integrity by design. Foreign keys prevent orphan marks/fees; a voucher must balance (debits = credits); marks can't exceed the total; a student can't have two placements in one year. These invariants are enforced in code and as database constraints.
